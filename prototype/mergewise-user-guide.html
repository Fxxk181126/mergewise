User Guide · Quick Start

5 分钟让 MergeWise 开始工作

MergeWise 是装在 GitHub 上的 AI 审查员：读 diff、标 Bug / 安全风险 / 缺测试，每个 PR 最多 2 条评论。它的默认工作方式是先安静观察、再开口说话——这份手册的前 5 步就是这条路径。

第 1 步 · 安装 GitHub App

1

安装并授权

打开 github.com/apps/mergewise（占位链接）→ 点击 Install → 选择授权范围：

  • All repositories：省事，但建议先不用——按仓库渐进接入更稳
  • Only select repositories：推荐 先挑 1–2 个活跃仓库试跑
MergeWise 申请的权限是 Pull requests（读写）、Contents（读 diff） 和 Issues（读，用于接收评论里的 mute 命令）。写权限仅用于发布评论，不修改你的代码——修复建议通过 GitHub 官方的 suggestion 机制提交，由你决定采不采纳。安装 GitHub App 需要仓库管理员权限。

拿不准就选 标准。这个值之后随时能在设置里改，而且 shadow 期结束后我们会根据你仓库的实际数据给一条建议值。

第 3 步 · Shadow 模式跑两周

3

"只看不说"的观察期

新仓库默认进入 shadow 模式：MergeWise 会分析每一个新 PR，但不发表任何评论，只在后台记录"如果开了评论，我会说什么"。

为什么需要这两周

  • 用你们自己的代码校准置信度门槛——不同代码库的"正常"长得不一样
  • 积累足够的样本（建议 ≥ 30 个 PR）让误报率报告有统计意义
  • 团队零打扰：没有人会被机器人的评论打断

什么时候可以提前结束

满足 30 个 PR 且 误报率报告连续 3 天 < 8% 时，设置页会出现"建议开启评论"的绿字提示。急着上线也可以直接手动开，但不推荐。

Shadow 期间可以在 Insights → 待观察池 看到所有"被拦下的发现"，提前了解它的口味对不对。

第 4 步 · 读误报率报告

4

开启评论前唯一要做的事

Shadow 满 14 天后，设置页会生成一份一页纸报告。只需要看三个数：

看什么健康值不健康时怎么办
误报率< 8%（可开启）报告会列出误报最多的 3 条规则——直接在报告里点"静音"再开启评论
预估每 PR 评论数≤ 2 条调高阈值（每 +0.05 约减 15% 评论），或把 P2 类并入汇总
P0 检出数≥ 1（说明它真在干活）为 0 属正常（不是每个 PR 都有高危），但连续为 0 建议先联系我们看看
这份报告也是给管理者的"可汇报证据"——截图放进周报，比任何宣传页都有说服力。

第 5 步 · 开启评论

5

一个开关，随时可退

设置页 → 评论模式 → 切到 Commenting。从下一个新 PR 起，团队就会看到 MergeWise 的第一条评论。

开启只影响之后的 PR，不会回头评论历史 PR；随时可以切回 shadow，已发的评论不受影响。任何团队成员都可以在 PR 里回复 @mergewise mute this 临时静音单个 PR。

日常 · 看懂 PR 里的评论

开启评论后，每个 PR 最多出现两种评论形态：

形态什么时候出现长什么样
行内评论 仅 P0（阻断级） 问题——安全漏洞、必然运行的 Bug 贴在出问题的那一行，附"建议修复"代码块，红色 P0 标记 + 置信度分数
汇总评论 其余所有达到阈值的问题（P1/P2） 每个 PR 固定只有一条，表格列出位置、级别、置信度

低于置信度门槛的发现不会出现——它们进的是后台的"待观察池"，永远不直接打扰你。命名、风格、格式类意见默认完全不做（那是 ESLint / Prettier 的职责）。

日常 · 应用修复建议

P0 行内评论和汇总里的 P1 条目都带 建议修复。两种用法：

  1. 单个应用：点评论里的 Apply suggestion——修复会作为 commit 直接进你的分支，提交人是你的名字，可 revert
  2. 批量应用：汇总评论底部 Apply all 一次采纳全部建议（逐条生成 commit，方便单独回滚）
每次 Apply 会回流为正样本——同规则在你仓库里的置信度会随之微升。也就是说，你采纳得越多，它在你仓库里说得越准。

日常 · 处理误报（最重要的一节）

误报一定会发生。MergeWise 的设计目标是让它只发生一次：

→

当一条评论是误报：点评论右下角的 👎（GitHub reaction），或在评论里回复 @mergewise mute this。
立刻发生三件事：这条评论被标记；生成一条仓库级抑制规则（同类代码不再触发同一规则）；误报率看板更新。

当一类问题你都不关心：在评论上回复 @mergewise mute rule missing-test，整条规则在本仓库静音——比如某些仓库确实不写测试，直接关掉这类提醒。

改主意了：设置 → 抑制规则，可以逐条撤销，撤销后立即恢复生效。

误报率 > 15% 的规则会自动降权（更难达到阈值），> 30% 自动静音并通知管理者。你不需要盯梢，机制会自己收敛。

日常 · 看板指标解读

Insights 页四个核心指标，以及"多少算健康"：

指标含义健康区间
每 PR 评论数开发者实际感知的打扰频率——我们的一等指标≤ 2 条 · 2–4 需调优 · > 4 立刻升阈值
误报率被标 👎（误报）的评论占比< 5% · 5–10% · > 10% 检查静音建议
建议采纳率被 Apply 或标记有效的比例（健康的反向信号）≥ 60% · 40–60% · < 40% 说明阈值太低
首条结论耗时从开 PR 到第一条评论出现的耗时p95 < 90s 即正常

每周一早上会有一封邮件摘要推送给管理者，花 60 秒就能掌握本周质量趋势（Slack / 飞书通道在路线图上）。

调优 · 置信度门槛

设置 → 置信度门槛。拖动滑块时右侧会实时显示影响："过去 30 天会发出多少条评论、平均每 PR 几条"。

你的情况建议动作
团队开始抱怨"说太多"阈值 +0.05（约减 15% 评论），观察一周
误报率抬头（> 8%）先看 Insights 静音建议，通常 1–2 条规则就能压下来，不必动阈值
感觉漏报多、想看得更全阈值 −0.05，同时确认评论策略仍是"聚合"，评论数不会失控
新仓库不知道从哪开始保持默认 0.80，跑完 shadow 期采纳报告建议值

调优 · 评论策略与范围

评论策略（三选一）

  • P0 行内 + 其余汇总（默认，推荐）：打断最少、高危最醒目
  • 全部行内：适合 < 5 文件的小 PR 团队，信息最全但评论多
  • 只发汇总一条：极度怕打扰的团队；P0 也会进汇总（不建议）

审查范围

默认开启三类：Bug / 安全风险 / 缺测试。可按仓库增删。风格、命名、格式、性能类永远不在范围内。

跳过路径

生成代码、迁移脚本、快照文件建议直接跳过，省额度也省噪音。设置里默认已带：

默认 skip 列表（可追加）
migrations/**   **/*.generated.ts   dist/**   **/*.snap   vendor/**

调优 · 抑制规则管理

每次点 👎 和 @mergewise mute rule 都沉淀在这里。设置 → 抑制规则：

  • 每条规则显示：来源规则 / 触发原因 / 创建人 / 创建时间 / 已避免的评论数
  • "已避免的评论数"很有意思——它是这个产品在你仓库里"学会安静"的直接证据
  • 团队复盘时建议过一遍：被静音的规则里有没有误杀？逐条 恢复 即可，立即生效

常见问题

支持哪些语言？

当前支持 TypeScript / JavaScript、Python、Go。Java 与 Rust 在路线图上（可在设置里投票加速）。

会拖慢 CI 或阻塞合并吗？

不会。MergeWise 不接入 CI 流水线，也不设必需的 status check。它只是"多看一眼的同事"，永远不挡路。

免费额度怎么算？

公开仓库永久免费；私有仓库按 ¥199 / 仓库 / 月（Team 版），含 14 天 shadow + 无限评论。前 20 个申请的仓库免费试用 30 天。

支持 GitLab / Bitbucket 吗？

暂不支持，当前专注 GitHub。GitLab 在评估中——可以在设置页留下你的邮箱，支持时第一时间通知你。

大 PR（100+ 文件）怎么办？

自动切换为分批审查：优先扫描风险高的文件类型（入口、鉴权、SQL、依赖变更），其余进汇总。增量 push 只审查新增 commit，不重复报旧问题。

机器人身份发的评论，reviewer 需要approve吗？

MergeWise 的评论不会阻塞合并，也不会计为 approve/request changes，不影响分支保护规则——但会在 PR 的 review 时间线里留下一条 MergeWise 的记录。
