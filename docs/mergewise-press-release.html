过去两年，AI 代码审查工具并不缺能力——缺的是分寸。开发者社区对这类工具最常见的评价不是"它找不到 bug"，而是"它太吵了"：一个中等规模的 PR 动辄收到七八条评论，其中近一半是命名和格式意见。MergeWise 今天给出的回答是一个反直觉的产品原则：一个 AI 审查员的价值，不取决于它说了多少，而取决于开发者敢不敢让它一直开着。

愿意付费与不敢常开之间的落差，正是 MergeWise 切入的位置。团队调研了主流工具（CodeRabbit、Copilot Code Review 等）在真实仓库里的表现后确认：开发者感知到的"误报率"，本质是"每个 PR 被打扰的次数"。所以 MergeWise 把产品的第一性指标定为——每 PR 评论数 ≤ 2。

三道闸门，把噪音挡在 PR 之外

GATE 01

置信度门槛

每条发现都带校准过的置信度分数。低于 0.80 的不进 PR，只进后台"待观察池"，用于下一轮校准——开发者永远看不到没把握的意见。

GATE 02

聚合评论

阻断级问题贴在代码行上，其余问题合并进唯一一条总结评论。命名、风格、格式类意见默认不做——那是 ESLint 和 Prettier 的工作。

GATE 03

误报闭环

点一次 👎（reaction）或回复 @mergewise mute this，即刻生成该仓库的抑制规则，同类代码永不再触发。误报率随使用持续下降，且在看板里完全透明。

对仍不放心的团队，MergeWise 默认以 shadow 模式接入：前两周只在后台运行、记录、不发表任何评论，用团队自己的代码校准阈值；管理者审阅误报率报告后，再决定是否开启评论。

你可能想问的三个问题

误报率要低到多少，才敢让它常驻团队仓库？

我们的答案是不承诺绝对值，承诺两件事：一是"每 PR ≤ 2 条评论"的打扰上限；二是误报可收敛——每一次"👎"或 @mergewise mute this 都变成仓库级抑制规则，内测仓库的误报率在 30 天内从 11.8% 降到 3.2%，曲线在看板里对客户完全公开。

我们的代码会被上传或用于训练吗？

Team 版仅在审查瞬间处理 diff 片段，不落库、不用于任何模型训练；Enterprise 版支持完全私有化部署（VPC / 内网），模型可切换为自建端点。

和 GitHub Copilot / CodeRabbit 的区别是什么？

它们优化"看得多"，我们优化"说得准"。具体差异：默认不做风格类意见、置信度不足不开口、每 PR 评论聚合、误报一键静音、新仓库先 shadow 两周。可以拿同一个 PR 并排跑一遍，评论数差距一目了然。
